# Отчёт по результатам анализа Kubernetes Audit Log

## Подозрительные события

1. Доступ к секретам:

- Кто: system:serviceaccount:secure-ops:monitoring
- Где: Пытался получить секрет в пространстве имен kube-system
- Почему подозрительно: Сервисный аккаунт monitoring из пользовательского неймспейса пытается получить доступ к системным секретам (например, default-token). Это нарушает принцип минимальных привилегий и может быть попыткой эскалации привилегий.

2. Привилегированные поды:

- Кто: Создатель привилегированного пода (скорее всего, system:serviceaccount:secure-ops:monitoring или пользователь с правами в неймспейсе)
- Комментарий: Создание пода с securityContext.privileged: true позволяет контейнеру получить доступ к хосту, что является критическим нарушением безопасности. Такие поды могут быть использованы для взлома ноды.

3. Использование kubectl exec в чужом поде:

- Кто: Оператор, выполняющий kubectl exec
- Что делал: Попытка выполнить команду cat /etc/resolv.conf в поде coredns в неймспейсе kube-system. Это может быть попыткой разведки или кражи конфиденциальной конфигурации.

4. Создание RoleBinding с правами cluster-admin:

- Кто: Пользователь или сервисный аккаунт, создавший RoleBinding
- К чему привело: Сервисный аккаунт monitoring получил права cluster-admin, что позволяет ему выполнять любые действия в кластере. Это явная эскалация привилегий.

5. Удаление audit-policy.yaml:

- Кто: Пользователь admin
- Возможные последствия: Удаление политики аудита отключает логирование событий безопасности, что позволяет злоумышленнику скрыть свои дальнейшие действия.

## Вывод
Анализ логов показывает явную попытку компрометации кластера Kubernetes. Злоумышленник использовал сервисный аккаунт monitoring для:
- Получения доступа к системным секретам
- Создания привилегированного пода
- Попытки выполнения команд в системных подах
- Эскалации привилегий через RoleBinding с правами cluster-admin
- Попытки отключения аудита для сокрытия действий
